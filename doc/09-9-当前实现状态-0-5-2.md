## 9. 当前实现状态（0.5.2）

仓库已包含可运行的最小可行实现：

- **Python 网关**（`server/`）：FastAPI 应用，OpenAI 兼容的 `POST /v1/chat/completions`（流式 + 非流式）、`GET /v1/models`、`GET /health`、WebSocket 端点 `WS /ws`。
- **Chrome 扩展**（`extension/`）：Manifest V3，包含 Service Worker、Content Script、MAIN world 注入脚本、Popup 界面与图标。
- **网络捕获双通道**：默认通过 `injected.js` 在主世界拦截 `fetch` / `XMLHttpRequest` 提供「有数据 / 流已结束」信号；若 10 秒内无任何网络信号，自动降级挂载 `chrome.debugger` 监听请求生命周期。
- **文本真相源 = DOM**：以目标页面的可见 DOM 为唯一回答文本来源，自动定位增量最大的最深容器；用户填了响应容器选择器时以用户为准。
- **一次性会话（开启新对话）**：每条回复提取完成并回传给网关之后，扩展会在**下一次请求发起前**
  把页面整页跳转回站点根路径（新对话页），使每个请求都在全新会话中发起。这样可避免两类问题：
  调用方（CLI / Agent）自己维护的上下文与网页侧残留的多轮上下文互相冲突；页面上残留的旧回复
  干扰 DOM 差异探测导致内容提取错位。
  **旧对话不会被删除**，仍保留在站点的历史记录中，只是不再被后续请求使用。
  该方式**不依赖任何站点 DOM 与选择器**，站点改版也不会失效，因此无需任何配置；
  代价是每轮请求前都会整页刷新一次页面。
  **导航由后台主导（0.5.0）**：Content Script 只在结果里带上 `needNewChat` 标记，真正的导航
  由 Service Worker 在**下一次任务到来时**执行，并等新文档的 Content Script 上报 `hello`
  （就绪信号）后才下发任务——「导航 → 等就绪 → 下发」严格串行。
  上一版由 Content Script 在回传后立刻跳转，会与客户端紧接着发起的下一轮请求抢跑：
  跳转尚未起步时 `tab.status` 仍是 complete，等待逻辑立即放行，任务被投递到正在卸载的旧文档后
  无声丢失（表现为「工具执行后扩展不再继续发送」）。
- **职责边界（本项目只做透传）**：本服务**不做 agent、不注入任何提示词、不实现工具执行**。Python 网关把扩展回传的内容**原样透传**给请求端；Agent / 工具执行是客户端的事。仓库已内置零依赖的 agents 客户端（见 `client/` 目录）。

- **工具调用：扩展只做纯透传，由 agents 客户端解析（流式/非流式均生效）**：模型完整输出后，
  扩展（Content Script 与 Service Worker）**都不解析**工具格式，而是把整段回答（可能是自然语言，
  也可能是工具调用的 JSON）**原样透传**进 `content`，`finish_reason` 为 `"stop"`。
  工具调用的解析与执行统一下移到客户端：
  - agents 客户端（`client/`）在每次请求时把「工具说明 + 调用约定」注入 system 提示词；
  - 模型按约定返回 `{"tool": "<名>", "args": {...}}`（裸 JSON 文本，多个调用用 JSON 数组），agents 客户端解析后执行工具并把结果回灌上下文，循环直至最终回答；
  - 该机制整体流程类 OpenAI function calling，但细节上依赖「提示词约定 + 文本透传」而非原生 `tool_calls` 字段。详见 `client/README.md`。

### 9.2 运行步骤

#### 启动网关

```bash
cd server
python -m pip install -r requirements.txt
python main.py            # 默认监听 0.0.0.0:8080
```

可用的环境变量（不填则取默认值）：

| 变量 | 默认值 | 含义 |
| --- | --- | --- |
| `OAP_HOST` | `0.0.0.0` | HTTP 监听地址 |
| `OAP_PORT` | `8080` | HTTP 监听端口 |
| `OAP_HEARTBEAT_SEC` | `15` | 网关主动 ping 扩展的周期（秒） |
| `OAP_HELLO_TIMEOUT_SEC` | `10` | 等待扩展握手消息的超时（秒） |
| `OAP_REQUEST_TIMEOUT_SEC` | `180` | 单次请求总超时（秒） |
| `OAP_QUEUE_WAIT_SEC` | `120` | 浏览器正忙时的最长排队时间（秒） |
| `OAP_PROMPT_MODE` | `all` | `all` 拼接全部 messages；`last_user` 只取最后一条用户消息 |
| `OAP_DEFAULT_MODEL` | `browser-proxy` | 回显给客户端的模型名 |
| `OAP_ALLOW_CORS_ANY` | `true` | 是否启用 `Access-Control-Allow-Origin: *` |

#### 安装 Chrome 扩展

1. 打开 `chrome://extensions/`，开启右上角「开发者模式」。
2. 点击「加载已解压的扩展程序」，选择本仓库的 `extension/` 目录。
3. 加载完成后，扩展会自动尝试连接 `ws://127.0.0.1:8080/ws`。

#### 第一次为某个站点配选择器

1. 打开目标 AI 网站（如 `https://chat.deepseek.com`），确认页面可用。
2. 点击扩展图标打开弹窗。
3. 把 `https://chat.deepseek.com` 设为活动标签页（弹窗会自动识别当前域名）。
4. 在 DevTools 中找到输入框和发送按钮，复制它们的 CSS 选择器，填入弹窗。
5. 「响应容器选择器」「响应请求 URL 匹配」可留空（走自动探测 / 关键词匹配）。
6. 会话处理无需配置：每条回复后扩展会把页面跳转回站点根路径（新对话页），不依赖任何选择器。
7. 「保留模型思考过程」默认**不勾选**：只返回最终答案。需要把模型的深度思考内容一并
   回传（以 `<think>…</think>` 包裹）时再勾选，详见 9.7 节。
8. 点击「保存当前站点配置」，再点击「发送测试」即可。

> 由于 extension 已声明 `"host_permissions": ["https://*/*"]`，首次加载会弹出全局站点权限警告，同意即可。

### 9.3 接口约定

- `POST /v1/chat/completions`：完全兼容 OpenAI Chat Completions 协议，支持 `stream=true/false`。
- `GET /v1/models`：返回当前可用的模型别名列表。
- `GET /health`：返回网关与浏览器连接状态（便于调试）。
- `WS /ws`：扩展客户端 WebSocket 入口，握手消息为 `{"v":1,"type":"hello","client_id":"…"}`，之后由网关下发 `execute` 指令。
- `POST /v1/cancel/{request_id}`：向扩展下发取消指令（尽力而为）。

请求级额外头：

| 头 | 用途 |
| --- | --- |
| `X-OAP-Host: chat.deepseek.com` | 指定目标站点域名；不指定时由扩展选择当前活动标签页 |
| `X-OAP-Timeout: 300` | 覆盖单次请求的总超时（秒），范围 5~3600 |

### 9.4 命令行联调

非流式：

```bash
curl -X POST http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "X-OAP-Host: chat.deepseek.com" \
  -d '{"model":"browser-proxy","messages":[{"role":"user","content":"你好"}]}'
```

流式：

```bash
curl -N -X POST http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "X-OAP-Host: chat.deepseek.com" \
  -d '{"model":"browser-proxy","stream":true,"messages":[{"role":"user","content":"讲个笑话"}]}'
```

### 9.5 已知限制（MVP 阶段）

- **MV3 Service Worker 会被回收**：纯 WebSocket 方案存在 30~60 秒不可用窗口，已通过 `chrome.alarms` 兜底 + Popup / Content Script 持久连接保活；长期稳定使用建议改用 Native Messaging（后续版本）。
- **单标签页串行**：一次只执行一个任务，新请求会按到达顺序排队，排队时间受 `OAP_QUEUE_WAIT_SEC` 限制。
- **文本源仅 DOM**：网络通道仅用于结束判定；如需做严格的 token 级流式（如打字机效果 + 复制按钮），后续可启用 `textSource: 'network'` 并为每个站点配置 JSON 提取路径。
- **`chrome.debugger` 警告横幅**：仅在降级路径下出现，会占用浏览器顶部一行（无法通过 API 抑制，只能在启动浏览器时加 `--silent-debugger-extension-api`）。
- **响应容器自动探测是启发式**：极端页面结构下可能选错容器，建议在弹窗里手动指定。
- **会话切换依赖整页跳转**：每轮请求前页面会跳转回站点根路径（新对话页）并刷新，因此
  标签页会短暂处于加载状态；后台会等新文档的 Content Script 就绪后再下发任务，但仍会带来
  一次可见的页面刷新。另外该方式默认「新对话页 = 站点根路径」，若目标站点的新对话页不在
  根路径（如 `/new`），需调整 `background.js` 中 `resetConversationIfNeeded()` 的拼装规则。
- **结束判定与网络信号（0.4.2）**：结束判定以「连续多次轮询文本无变化」为准——收到流结束信号后约
  2.4 秒、无信号时约 10 秒。为防「生成到一半就结束」，网络通道做了三重收紧：
  (1) 结束信号之后若页面文本仍在增长（超出 1 秒渲染滞后宽限），判定该信号不代表答案流结束，退回长窗口；
  (2) 嗅探读取失败不再被当作流结束，改由 DOM 长窗口兜底；
  (3) 未产生任何数据的空响应 / 心跳请求不再上报结束信号，debugger 降级路径也改为等所有被跟踪请求都结束才上报。
- **工具调用不在扩展侧解析（0.5.1）**：扩展只把模型的完整输出原样透传，`tool_calls` 一律由客户端解析。
  这样能借助客户端的**括号闭合校验**可靠拒绝「半截 JSON」；扩展侧则通过「未闭合 JSON 不判定完成」
  与「疑似工具调用时延长稳定窗口（约 4.8 秒）」两道防护，避免把还没输出完的 JSON 当作最终结果回传或执行。
  旧版由 Service Worker 用宽松正则自行解析 `tool_calls` 并直接回传，会绕过客户端的完整性防护，
  把「思考中输出的、尚未完全输出的 JSON」当作完整调用直接送执行。
- **任务可靠性与兜底（0.5.0）**：为避免「指令丢失后扩展卡死」，后台新增四道保障：
  (1) 下发 `run` 后若 15 秒内收不到 Content Script 的 `accepted` 回执，会重试下发一次，
      仍无回执则向网关报错并释放任务——不再让 `currentTask` 永久悬挂、导致后续请求全被 `browser_busy` 拒绝；
  (2) 每个任务都有硬超时兜底（网关超时 + 10 秒），到点强制释放并报错；
  (3) `ensureContentScript` 注入失败时直接向网关报 `injection_failed`，不再静默继续；
  (4) 页面刷新时旧连接的 `onDisconnect` 不再误删刚建立的新连接。

### 9.6 提示词配置（根目录 .txt，热加载）

所有「发给 AI 的提示词」都已从代码里剥离到仓库根目录的 4 个 `.txt` 文件，
直接编辑即可，**无需重启服务**：每次请求只对文件做一次 `stat`，按修改时间判断
是否需要重新读取，未变化则复用缓存。

| 文件 | 作用 | 使用方 |
| :--- | :--- | :--- |
| `prompt_template.txt` | 消息包装模板：决定 messages 拼成什么文本后再粘贴进网页输入框 | 服务端 `server/main.py` |
| `system_prompt.txt` | 默认系统提示词：请求未携带 `role: system` 消息时自动注入 | 服务端 `server/main.py` |
| `agent_system_prompt.txt` | Agent 默认系统提示词 | 客户端 `client/cli.py`（`--system` 默认值） |
| `tool_call_format.txt` | 工具调用 JSON 格式约定 | 客户端 `client/prompts.py` |

**文件来源**：这 4 个文件**不纳入版本控制**（已写入 `.gitignore`）。首次运行客户端
CLI（`python -m client.cli`）或启动网关时会自动生成；之后可随意编辑，程序只会补齐
缺失的文件，不会覆盖已有内容。

**容错策略**：任一文件被删除、无法读取或内容为空时，自动回退到代码内置的等价内容，
并只告警一次，服务照常启动与运行；下次启动时再补回一份默认文件。

#### prompt_template.txt 语法

- 占位符：`{system}`（所有 system 消息合并）、`{user}`（所有 user / assistant 消息合并）；
- 条件块：`{{#system}} … {{/system}}`、`{{#user}} … {{/user}}`，起止标签各占一行，
  对应内容为空时整块丢弃（**不支持嵌套**）；
- 注释行：以 `#` 开头的行不发送给模型；
- 连续 3 个以上换行会被压缩为 2 个。

默认模板的渲染结果：

```
<system>
{system 内容}
</system>
<user>
{user 内容}
</user>
```

想改成别的写法（如 `角色设定：{system}` / `问题：{user}`）直接改文件即可。
**注意**：若把 `<system>` / `<user>` 标签换成其它标记，请同步检查扩展侧
`extension/content.js` 的 `cleanReplyText()` 清理正则，否则包装标签可能被当成
回答内容回传。

#### system_prompt.txt 说明

- 请求中**已带** `role: system` 消息时，以请求为准，不注入本文件；
- 请求**没有** system 消息时才注入本文件内容；
- 把本文件清空（或删除）即可恢复「完全不注入默认系统提示词」的原始行为。

### 9.7 模型思考过程的处理（`keepThinking`）

带「深度思考 / 思维链」的站点（DeepSeek R1、各类 Reasoning 模型）在输出最终答案前，
会先在页面上渲染一段可折叠的思考过程（常见标题为 `Thought for N seconds`、
`已深度思考（用时 N 秒）` 等）。

扩展对这段内容的取舍由**站点级开关 `keepThinking`** 控制（弹窗「站点配置」内）：

| 开关 | 行为 | 返回示例 |
| :--- | :--- | :--- |
| **关闭（默认）** | 只返回最终答案，思考过程被丢弃 | `这是最终答案…` |
| **开启** | 思考过程以 `<think>` 包裹在前，最终答案在标签之外 | `<think>…思考正文…</think>\n\n这是最终答案…` |

要点：

- **默认关闭**。未配置过该站点的 profile 时读到 `undefined`，语义即「丢弃」，
  因此已保存的旧配置无需任何改动即可升级。
- 开关只影响**扩展提取阶段**（`extension/content.js` 的 `readReplyText()` / `cleanReplyText()`），
  服务端与客户端均**原样透传**、不做二次加工。
- 无论开关状态，最终答案里都不会混入思考正文：主文本由「容器全文 − 思考块正文」得到，
  减法走**归一化匹配**（`removeNormalized()`，忽略空白与零宽字符差异），
  避免旧版字面量 `split` 因渲染差异失效而导致思考内容重复输出。
- 折叠标题（如 `Thought for 2 seconds`）一律被剔除，且匹配边界**精确到时间单位为止**——
  标题与正文被拼在同一行时也不会误删整段正文。
- 剥离思考后主文本为空（答案被整体包在思考块内的站点）时，回退为「已去标题的思考正文」，
  保证回复不丢失。
- **思考进行中的占位不会被当成回复（0.4.1）**：模型思考期间页面只显示临时标题
  （如 DeepSeek 的 `Thinking`、中文站的 `思考中`），此时最终答案尚未产出。这类文案
  不带时间量，扩展单独识别（`isThinkPlaceholder()`），一旦命中即视为「无内容」——
  不计稳定计数、不置 `hasContent`，因此不会在思考阶段提前收尾（旧版会返回 `Thinking`，
  或 DOM 标题节点重复拼接成的 `ThinkingThinking`）。兜底读取容器全文时也会先整块剔除
  思考块，从源头避免标题混进答案。
- **思考块内部的元素不会被当成回复容器（0.5.2）**：思考块里的 markdown 段落
  （如 DeepSeek 的 `<p class="ds-markdown-paragraph">`）自身不含 `think` 关键词、
  后代里也没有思考块，原先的 `isThinkBlock()`（查自身）与 `containsThinkBlock()`（查后代）
  **都发现不了它**，于是这段思考内容会被当作「最深的回复容器」选中并读出——关闭开关时
  就表现为「只返回思考内容」，且时好时坏（取决于思考与答案的渲染时序）。
  现新增 `isInsideThinkBlock()` **向上查祖先链**，在容器选择阶段排除这类元素。
- **实在取不到答案时的兜底（0.5.2）**：若直到超时都没有产出最终答案、而页面确实只有思考内容，
  会把它用 `<think>…</think>` 包裹返回（`finish_reason` 为 `length`），客户端可识别并灰显，
  不会再把思考正文当成正常答案返回。

想保留思考内容做展示的客户端，可自行按 `<think>…</think>` 拆分；仓库自带的
`client/cli.py` 会把该标签内的内容渲染成浅灰色。
